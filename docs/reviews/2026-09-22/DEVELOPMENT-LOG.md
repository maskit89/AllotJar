### W01 foundation notes for the next developer

`Transaction` records account movement; `TransactionSplit` records budget attribution. Transfers currently cannot be split across budget lines. Add a distinct jar-allocation model rather than allowing transfers to masquerade as income or expenses.

The candidate model is signed, dated allocations associated with an operation, jar and account; transaction-backed entries also identify the relevant transaction/account leg. Initial allocations and same-account reallocations divide existing account money and create no bank movement. Unallocated funds reconcile account actuals minus signed jar balances. This is a technical design proposal, not yet deployed schema or a new product rule.

Implementation must cover:

1. Dated account openings (the current `Account` has no opening date), jar designation and ownership/currency validation, and persistent operation identity.
2. Initial allocation, transaction funding/withdrawal splits and same-account reallocation; outgoing funds identify the jar/unallocated sources.
3. Completed cross-account transfers with explicit user confirmation and idempotent pairing of imported statement sides.
4. One shared dated balance service used by JarBalances, BudgetActuals savings availability, CreateJar responses and account reconciliation. Planned amounts must never enter actual sums.
5. All write paths: create/update/delete transaction, transfers, both imports, allocation commits and account-opening edits. A protected manual-transfer path alone leaves bypasses.
6. Automatic savings-line jars in AddBudgetItem, templates and registration seeding must obtain a savings-account selection. Do not create valid-looking unbacked jars or assign an arbitrary account.
7. Account deletion must not detach jar/transaction history. Additive schema changes must preserve development data until handling is agreed; no invented opening dates or planned-as-actual backfill.
8. SQL transaction/concurrency protection for withdrawals. Read-then-save sufficiency checks alone can overdraw savings under concurrent requests.

Questions still relevant before affected foundation paths are activated: handling existing local sample data with missing account/opening date (O12), import reconciliation/order (O1), changing a jar's designated account after money/history exists (O3). Account/budget currency policy was answered in rule63; do not ask it again. Questions on unrelated features do not block the bounded fixes above.

## W11 Pocket-money identity and archive (rules 53–54; REVIEW A6) — 27 September 2026

**Scope.** A person's pocket-money budget line is linked to their permanent id rather than their display name; renaming them renames the line and a later sync reuses it (rule 53); archiving them stops their planned pocket money from the next month onward, including months already created, asks whether to keep or cancel the current month's remainder, and never touches a recorded payment or an account balance (rule 54).

**Application.** `BudgetItem.MemberId`, until now income-only, is also the person link on a pocket-money expense line; it is set only by `SyncPocketMoneyLinesCommandHandler`, which now matches each active member's line by id first, adopts an unlinked line of the same name (case-insensitive) by stamping the id, renames the line to the member's current name and creates missing lines with the id. The user-facing "assign a person" write paths still refuse expense lines. New `Household/PocketMoneyLines`: `ForCurrentMonthAsync` (each person's planned/paid/remaining on the calendar current month, using `BudgetActuals` so "paid" is the line's actuals), `RenameAsync` (every month's expense line carrying the id), `StopFromNextMonthAsync` (from the current month on: a future line with nothing recorded against it is removed, one with a payment is cut to what was paid; the current month's line is left alone unless the caller asks to cancel, which cuts it to what was paid; past months untouched). `UpdateHouseholdMemberCommandHandler` calls `RenameAsync` when the name changes; `ArchiveHouseholdMemberCommand` gains `CancelCurrentMonthPocketMoney` and the handler calls `StopFromNextMonthAsync` on archive (a restore recreates nothing; the sync re-adds a restored person on request). `CreateBudgetMonth` (copy from previous) no longer copies an archived person's pocket line (income lines attributed to them still copy as whole-household). `HouseholdMemberDto.PocketMoneyThisMonth` (`MemberPocketMoneyDto` planned/paid/remaining, null without a line) is filled by the members list and the single-member reads, always for the calendar current month whatever month is selected. API: `PUT /members/{id}/archive {archived, cancelCurrentMonthPocketMoney}`. No migration: the column and index already exist.

**Client.** People page: the ✕ archives on one click as before unless `pocketMoneyThisMonth.remaining` is positive, in which case an "Archive {name}" dialog explains that pocket money stops from next month and payments stay, states "This month still plans €X for {name} (€Y already paid out)." and offers **Keep this month's remaining pocket money** (default) or **Cancel the remaining amount**; confirming sends the flag. `HouseholdMemberDto.pocketMoneyThisMonth` typed. USER_GUIDE gains "Pocket money, renaming and archiving".
