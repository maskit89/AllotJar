### W01 foundation notes for the next developer

`Transaction` records account movement; `TransactionSplit` records budget attribution. Transfers currently cannot be split across budget lines. Add a distinct jar-allocation model rather than allowing transfers to masquerade as income or expenses.

The candidate model is signed, dated allocations associated with an operation, jar and account; transaction-backed entries also identify the relevant transaction/account leg. Initial allocations and same-account reallocations divide existing account money and create no bank movement. Unallocated funds reconcile account actuals minus signed jar balances. This is a technical design proposal, not yet deployed schema or a new product rule.

Implementation must cover:

1. Dated account openings (the current `Account` has no opening date), jar designation and ownership/currency validation, and persistent operation identity.
2. Initial allocation, transaction funding/withdrawal splits and same-account reallocation; outgoing funds identify the jar/unallocated sources.
3. Completed cross-account transfers with explicit user confirmation and idempotent pairing of imported statement sides.
4. One shared dated balance service used by JarBalances, BudgetActuals savings availability, CreateJar responses and account reconciliation. Planned amounts must never enter actual sums.
5. All write paths: create/update/delete transaction, transfers, both imports, allocation commits and account-opening edits. A protected manual-transfer path alone leaves bypasses.
6. Automatic savings-line jars in AddBudgetItem, templates and registration seeding must obtain a savings-account selection. Do not create valid-looking unbacked jars or assign an arbitrary account.
7. Account deletion must not detach jar/transaction history. Additive schema changes must preserve development data until handling is agreed; no invented opening dates or planned-as-actual backfill.
8. SQL transaction/concurrency protection for withdrawals. Read-then-save sufficiency checks alone can overdraw savings under concurrent requests.

Questions still relevant before affected foundation paths are activated: handling existing local sample data with missing account/opening date (O12), import reconciliation/order (O1), changing a jar's designated account after money/history exists (O3). Account/budget currency policy was answered in rule63; do not ask it again. Questions on unrelated features do not block the bounded fixes above.

## Jar allocation slice (W01 jars, W05 jar cutoff; rules 1–6, 9, 26, 40, 48, 67, 68, 70, 73–81) — 26 September 2026

**Decisions taken first.** Rules 73–81 were agreed in conversation on 26 September (see AGREED-RULES): every jar has a designated account of any non-credit-card type; no account may go negative; credit cards are not accounts; optional bank identifiers; "saved so far" is a dated initial allocation; incoming money prompts for allocation when recorded (deferred to the next slice); outgoing money identifies its jar through the budget line; a jar's account changes only at zero balance; accounts-first onboarding with no sample data and no template savings lines, after research on EveryDollar, YNAB, Monarch, Goodbudget, Actual Budget, Monzo Pots and Starling Spaces (accounts-first apps ask for balances first because only money on hand can be assigned; none pre-loads sample data; goal forms are the same fields everywhere).

**Schema** (`20260926153122_JarLedgerAllocations`): `Jars.FundingAccountId` NOT NULL with a Restrict foreign key to Accounts; `Jars.OpeningBalance`/`OpeningAsOf` dropped; new `JarAllocations` (OwnerId, AccountId, Kind InitialAllocation/Reallocation/Movement, Date, TransactionId cascade, Note, CreatedUtc) and `JarAllocationPostings` (JarId Restrict, Amount 18,4); unique filtered index `(TransactionId, AccountId)`; `Accounts.Iban/Bic/SortCode/AccountNumber`. The migration first deletes jars with no (or a dangling) account: pre-launch data only (rule 65); their savings lines become plain lines through the existing SetNull key and their transactions are untouched. Nothing is invented.

**Domain.** `ActualSavingsLedger.Calculate` accepts any non-credit-card account, keeps a re-designated jar's zero-sum history reconcilable, and exposes `PositiveAllocations`/`HasBackingDeficit` (rule 70). `ActualAccountLedger.Entries` is public so the application reader can attribute movements. `BudgetItem.Jar` navigation added.

**Application.** `JarLedgerReader` is the single jar read path: per jar-backed account it reads the account ledger, takes the stored allocations (a transaction-linked allocation whose postings no longer match its transaction is set aside and counted as unreconciled rather than failing the read), derives rule-79 attribution for every other movement (expense on a jar's line from the jar's account → that jar, split slices likewise, anything else → unallocated) and calls the domain ledger; `Apply` produces the candidate ledger for rule 68/70 checks. `CreateJar` requires the account (owner, not credit card) and records the initial allocation as a zero-sum operation validated against unallocated funds as of its date (not future, not before the account opening) under `BeginLedgerWriteAsync` — a ReadCommitted transaction holding `UPDLOCK, HOLDLOCK` on the account row on SQL Server, null on InMemory. `ReallocateJarMoney` (POST `/api/jars/reallocations`) moves money between one account's jars/unallocated with rules 68/70 under the same lock; cross-account is refused with a pointer to transfers (rule 7). `GET /api/jars/ledger` returns each account's balance, jars, unallocated, positive allocations and deficit flag. `UpdateJar` allows an account change only at zero balance (rule 80); `ArchiveJar` requires zero (rule 26). `GetJars`, `BudgetActuals.SavingsAvailable` (as of month end, today for the current/future month; null when unavailable), `CreateBudgetMonth` seeding (balance as of the day before the month) and account reconciliation (In jars, Unallocated, `HasBackingDeficit`) read the ledger; `JarBalances` is deleted. `TransactionInvariants.EnsureJarAccount` refuses attributing a payment (whole or slice) to a jar's line unless it leaves the jar's account, on every path (create, assign, update incl. account change, split, import). `AddBudgetItem` refuses savings-group lines (jars come from the jar form, which plants the line). `DeleteAccount` refuses accounts holding jars or allocation history. Accounts: `BankIdentifiers` normalises and format-checks the optional fields; validators refuse credit cards (rule 75) and negative openings (rule 74). Onboarding: `BudgetSeeder`, `StarterSavingsKindSeeder`, the startup backfill and `RegisterRequest.IncludeSampleData` are removed; `HouseholdBootstrap` seeds nothing; templates carry no savings groups.

**Choices within the rules (object if wrong):** initial allocation date defaults to today, backdatable to the account opening date; a stored allocation that drifts from its transaction is set aside for review rather than blocking every read of the account; a re-designated jar keeps its zero-sum history in the old account; expenses from a jar-backed account assigned to a non-jar line draw from unallocated for now (the rule-79 prompt arrives with the next slice, together with rule 78 incoming prompts, cross-account "Move money" via transfers, and rule 74 enforcement on manual entry/import holds).
